## 2. The component model the owner asked for

Every **area** (classification, forecasting, unsupervised, rl, causal) is served through three **components**,
each a plugin chosen by JSON configuration, each replaceable by an external implementation:

| Component | What it does | What exists today | Entry-point group (target) |
|---|---|---|---|
| **Input** | Turns what the person gives (sentence, text, JSON, CSV, envelope, Telegram message) into a validated typed request. Contains the **LLM interpreter** (chooses declared values only) and the **readers**. | `m5phet.interpret` (one command, `hermes` or `tools/interpreter_ollama.py`), `web/engine.parse_file`, `orchestrate.route`, `Engine.execute(dry_run=True)` | `m5phet.interpreters` (WP03), readers stay in `web/engine.py` |
| **Core** | The fitted engine that answers: Laya, TensorFlow bundle, sklearn regimes, SB3 policy, EconML study. Includes the **temporal representation** the engine consumes (windows, lags, features, calendar availability). | the five providers under `m5phet.providers`; representation is fixed inside each fitted state | `m5phet.providers` (exists); representation design = WP06 |
| **Output** | The **output header** (what kind of structured result this area returns: `output_kind`, units, statuses, refusal codes) and the **output procedure** (how answers are rendered/narrated/exported: deterministic render, checked narration, JSON export, Telegram text). | `questions.py` answer shapes, `domain_outputs.py`, `orchestrate.render/narrate/narration_problems`, UI `renderEnvelopeAnswers` | `m5phet.outputs` (WP04) |

**Per-area meaning of "Output" (the owner's words, made concrete):**
- causal → estimand + effect + interval + assumptions, or `NOT_ESTIMABLE`; procedure: effect table, never a p-value that was not computed;
- rl → proposed action in the policy's own scale + critic value, `execution_authorized: false`; procedure: "a score is not an order" always stated;
- unsupervised → cluster assignment of the supplied rows under a fitted reference + description of the cluster satisfying a declared metric; procedure: cluster table + novelty;
- forecasting → target/horizon-indexed point (unit, scale) and, once a quantile bundle exists, intervals; procedure: numbers with units;
- classification → label + uncalibrated probabilities + the exact instruction scored; procedure: probability bars marked uncalibrated.

### WP06 — Automated temporal representation design from data (doctoral core; explicit jobs, never in chat inference)
This is the piece the owner's doctoral proposal compares across stages. It is **not** an inference question;
it is an explicit `design` job followed by explicit `fit` and `evaluate` jobs, each producing an artifact.
- Repo: `feature-eng` (design + features), `predictor` (fit), `M5PHET/evaluation` (evaluate + closure table),
  `doin-node`/`doin-plugins` (search, later).
- Stage 1 — **representation spec** (`M5PHET/docs/REPRESENTATION_SPEC.md` + `src/m5phet/representation.py`): a JSON
  object naming windows, lags, differencing, calendar availability clocks (publication vs receipt), features by
  name from `feature-eng`, and the fitted-state reference it produces. Validated like an envelope. Test: a spec
  round-trips and a foreign feature name is refused.
- Stage 2 — **design job** (`feature-eng`: `feature_eng_m5phet/design.py`, CLI `m5phet-representation design
  --data X.csv --out spec.json`): from the dataset profile only (columns, types, sampling, stationarity and
  seasonality tests that already exist in feature-eng), emit **candidate specs** with the test results that
  motivated each (why this window, why this lag). No model is fitted here. Test on a synthetic series with a
  known period: the candidate set contains that period.
- Stage 3 — **fit job**: `predictor` trains one bundle per candidate spec with the existing configs (memory-capped,
  5090 only, owner admits each dispatch). Output: exported bundles with `representation_spec` embedded in the
  manifest, so the forecast provider can show which representation answered.
- Stage 4 — **evaluate**: `M5PHET/evaluation` scores each bundle on an untouched holdout with the naive reference
  on the same rows and emits the owner's closure table; `NOT_COMPARABLE` when rows differ.
- Stage 5 — **search** (only after 1–4 work by hand): a DOIN/DEAP adapter that proposes the next candidate spec
  from the evaluated ones; one scalar objective, full metrics kept beside it. Not before the owner's go.
- Proof at each stage: its own tests plus one end-to-end run on the household dataset (already local) producing
  a table; the table is the deliverable, not a claim.
- Done-when: the forecast provider's catalog shows, per bundle, the representation spec that produced it, and the
  evaluation report ranks candidates with the closure table.

# Revision 2 — 2026-09-25: Laya as the first layer of every area, and where the data comes from

**Why this revision.** The owner restated the design on 2026-09-25: Laya is not one provider among five; it is the
**first cognitive layer of every area**. In classification it answers end to end (that exists). In every other area it
**chooses the configuration** — the preprocessing per feature, the grouping of features, the extractor per group, the
core over the fused branches, the clustering method and its parameters, the causal estimator and its nuisance models,
the trading decision to evaluate — and the chosen configuration is then fitted and measured by the explicit jobs the
plan already has (WP06 stages 3–5, WP13). That is the doctoral proposal: **a data-driven, Laya-chosen temporal
representation and pipeline, compared on the closure table against the hand-made baseline and the searched one**.
The owner also asked that a sentence may name a dataset from the data lake instead of attaching a file.

**What Laya is, so nobody asks it for what it cannot give.** Laya answers *state + typed choice questions → typed
answers with uncalibrated probabilities* (news-signal `laya_news`, `answer_questions`). Therefore, everywhere below,
"Laya chooses X" means exactly: the framework writes a **state** (a structured, textual description: the dataset
profile, a feature's metric sheet, the problem statement), asks a **`choice` question whose options are DECLARED**
(registered plugins, declared parameter grids, fitted references), and records the answer as a **decision record**
(state digest, options, chosen label, uncalibrated probabilities, checkpoint). Laya never invents an option, never
sees rows beyond what the state carries, never fits anything, never authorizes anything. Its choices are hypotheses;
the closure table is the judge. If a package below cannot be built that way, stop and say so.

### WP22 — The causal question that matters: EUR/USD's transient response to calendar events (replaces "WP10 second half")

**The owner's formulation (2026-09-25).** Like a circuit hit by several pulses and steps at different past instants, the
EUR/USD's volatility and trend respond to the economic-calendar releases that occurred inside a past window; the
question is the **sensitivity** of that response to each event, given what was *expected* (consensus) and what
*resulted* (actual) for every event in the window — and it must be climbed on the **full causal ladder**
(association → intervention → counterfactual), so it is not a correlation and it is not confounded by the other events,
the hour, the regime or the volatility that was already there.

**What this is in the literature, so the successor uses the right tools and no invented ones.** An *event study* with
*local projections* (Jordà 2005): for horizon `h` after instant `t`, `y[t+h] − y[t] = Σ_k β[k,h] · s_k(t) + γ·controls(t)
+ ε`, where `s_k` is the **standardized surprise** of event `k` (`(actual − consensus) / σ_k`) and `β[k,h]` is the
**impulse response** of event `k` at horizon `h` — the transient. Several events in the window are several `s_k`;
additivity (superposition) is a testable hypothesis, not an assumption (interaction terms are the alternative).
Identification (rung 2): the surprise is as-good-as-random **conditional on the pre-release information set** (the
consensus, the previous releases, pre-event volatility, hour-of-day, regime) — the standard macro-announcement
identification (Andersen–Bollerslev–Diebold–Vega 2003; Gürkaynak–Sack–Swanson 2005). Heterogeneity: EconML DML with
`s_k` as continuous treatment and effect modifiers = regime, pre-event volatility, surprise sign → CATE (that is where
WP20's space is used). Rung 3 (counterfactual): the fitted structural path with one event's surprise set to zero, shown
**as model-based**, never as an observation.

**Data and clocks (what exists).** `feature-eng/app/economic_calendar.py` already computes `release_surprise` (the last
consensus PUBLISHED before the actual), `available_surprise` (received), `revision_surprise`, and refuses
`MISSING_PUBLICATION_CLOCK`; the surprise used here is `release_surprise` and **only** information with a publication
clock before `t` may enter `controls(t)`. EUR/USD bars: locate them first (`predictor/examples/data`, `financial-data`,
`feature-eng` examples; report the file, its step and its span; never download). The calendar dataset: the one mapped in
`USE_CASES.md` UC-02 (locate; if it is not on disk, `NOT_RUN` naming what is missing).

**Steps (each an artifact; each tested; nothing in chat inference).**
1. **Event window builder** (feature-eng, `feature_eng_m5phet/events.py`): for every release `k` at `t_k` with a
   publication clock, the outcome paths `log_return[t_k, t_k+h]` and `realized_vol[t_k, t_k+h]` for
   `h ∈ {5, 15, 30, 60, 240} min` (declared), the standardized surprise, the consensus, and the **other releases inside
   the window `W` (24 h, declared)** with their surprises and offsets — one row per (event, horizon). A release without
   consensus or without a publication clock is excluded by name and counted. Test on a synthetic calendar + synthetic
   bars with a planted impulse response.
2. **Rung 1 — association**: correlations and the naive response table (mean outcome by surprise sign) — the naive
   reference for the closure table. Deterministic.
3. **Rung 2 — intervention**: (a) local-projection OLS with HAC (statsmodels) per event and horizon → `β[k,h]` with
   intervals, controls declared; (b) EconML DML through WP20's `prepare-study --spec` for the heterogeneous version,
   treatment `s_k`, modifiers from the declared roles (regime from the unsupervised area's assignment when available,
   pre-event volatility, sign). Superposition test: additive vs interaction model on held-out events. **Placebo**:
   pseudo-events at times with no release must give `β ≈ 0` within intervals, else the study is `NOT_IDENTIFIED` and
   says so.
4. **Rung 3 — counterfactual**: `counterfactual_path(window, zero_out=k)` from the fitted additive model, labelled
   `MODEL_BASED_COUNTERFACTUAL`, with the interval propagated; refused when the additive model failed the
   superposition test.
5. **Envelope**: the causal provider declares three new question types — `impulse_response{event, horizons?,
   outcome: return|volatility}`, `sensitivity{events: [...], outcome, window}`, `counterfactual_path{window, zero_out}`
   — each answered from a fitted event study by name, refused `NOT_ESTIMABLE` by the ATE-only studies, and shown in the
   workbench as a **response-path table** (the output plugin: horizon × β × interval; no plot is required).
6. **Evaluation**: held-out events by time (the last 20 % of the span), the closure table per outcome and horizon with
   the naive response as reference, placebo results, and the `COMPARABLE` verdict rules; `causal_accuracy` stays refused
   unless a planted-effect synthetic run is the comparison (then it is a recovery test, not a market claim).
7. **Laya's part** (after WP17/WP20): Laya chooses, among the declared options, the estimator, the nuisance models, the
   window `W`, the horizon set and the modifiers, from the metric sheet of the event window (WP18 step 1 applied to
   the event rows); the spec then goes through step 3 unchanged; the table compares `hand_spec` vs `laya_spec`.
- Repos: feature-eng worktree (1, 2, 6 helpers), causal-inference-m5phet-provider (3b, 4, 5), M5PHET (5 output
  rendering, 6 table).
- Proof at each step: tests plus the real run on the located EUR/USD + calendar data, memory-capped, CPU; paste the
  `β[k,h]` table for the events that were present, the placebo result and the superposition verdict.
