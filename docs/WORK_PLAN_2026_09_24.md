## 2. The component model the owner asked for

Every **area** (classification, forecasting, unsupervised, rl, causal) is served through three **components**,
each a plugin chosen by JSON configuration, each replaceable by an external implementation:

| Component | What it does | What exists today | Entry-point group (target) |
|---|---|---|---|
| **Input** | Turns what the person gives (sentence, text, JSON, CSV, envelope, Telegram message) into a validated typed request. Contains the **LLM interpreter** (chooses declared values only) and the **readers**. | `m5phet.interpret` (one command, `hermes` or `tools/interpreter_ollama.py`), `web/engine.parse_file`, `orchestrate.route`, `Engine.execute(dry_run=True)` | `m5phet.interpreters` (WP03), readers stay in `web/engine.py` |
| **Core** | The fitted engine that answers: Laya, TensorFlow bundle, sklearn regimes, SB3 policy, EconML study. Includes the **temporal representation** the engine consumes (windows, lags, features, calendar availability). | the five providers under `m5phet.providers`; representation is fixed inside each fitted state | `m5phet.providers` (exists); representation design = WP06 |
| **Output** | The **output header** (what kind of structured result this area returns: `output_kind`, units, statuses, refusal codes) and the **output procedure** (how answers are rendered/narrated/exported: deterministic render, checked narration, JSON export, Telegram text). | `questions.py` answer shapes, `domain_outputs.py`, `orchestrate.render/narrate/narration_problems`, UI `renderEnvelopeAnswers` | `m5phet.outputs` (WP04) |

**Per-area meaning of "Output" (the owner's words, made concrete):**
- causal → estimand + effect + interval + assumptions, or `NOT_ESTIMABLE`; procedure: effect table, never a p-value that was not computed;
- rl → proposed action in the policy's own scale + critic value, `execution_authorized: false`; procedure: "a score is not an order" always stated;
- unsupervised → cluster assignment of the supplied rows under a fitted reference + description of the cluster satisfying a declared metric; procedure: cluster table + novelty;
- forecasting → target/horizon-indexed point (unit, scale) and, once a quantile bundle exists, intervals; procedure: numbers with units;
- classification → label + uncalibrated probabilities + the exact instruction scored; procedure: probability bars marked uncalibrated.

### WP06 — Automated temporal representation design from data (doctoral core; explicit jobs, never in chat inference)
This is the piece the owner's doctoral proposal compares across stages. It is **not** an inference question;
it is an explicit `design` job followed by explicit `fit` and `evaluate` jobs, each producing an artifact.
- Repo: `feature-eng` (design + features), `predictor` (fit), `M5PHET/evaluation` (evaluate + closure table),
  `doin-node`/`doin-plugins` (search, later).
- Stage 1 — **representation spec** (`M5PHET/docs/REPRESENTATION_SPEC.md` + `src/m5phet/representation.py`): a JSON
  object naming windows, lags, differencing, calendar availability clocks (publication vs receipt), features by
  name from `feature-eng`, and the fitted-state reference it produces. Validated like an envelope. Test: a spec
  round-trips and a foreign feature name is refused.
- Stage 2 — **design job** (`feature-eng`: `feature_eng_m5phet/design.py`, CLI `m5phet-representation design
  --data X.csv --out spec.json`): from the dataset profile only (columns, types, sampling, stationarity and
  seasonality tests that already exist in feature-eng), emit **candidate specs** with the test results that
  motivated each (why this window, why this lag). No model is fitted here. Test on a synthetic series with a
  known period: the candidate set contains that period.
- Stage 3 — **fit job**: `predictor` trains one bundle per candidate spec with the existing configs (memory-capped,
  5090 only, owner admits each dispatch). Output: exported bundles with `representation_spec` embedded in the
  manifest, so the forecast provider can show which representation answered.
- Stage 4 — **evaluate**: `M5PHET/evaluation` scores each bundle on an untouched holdout with the naive reference
  on the same rows and emits the owner's closure table; `NOT_COMPARABLE` when rows differ.
- Stage 5 — **search** (only after 1–4 work by hand): a DOIN/DEAP adapter that proposes the next candidate spec
  from the evaluated ones; one scalar objective, full metrics kept beside it. Not before the owner's go.
- Proof at each stage: its own tests plus one end-to-end run on the household dataset (already local) producing
  a table; the table is the deliverable, not a claim.
- Done-when: the forecast provider's catalog shows, per bundle, the representation spec that produced it, and the
  evaluation report ranks candidates with the closure table.
