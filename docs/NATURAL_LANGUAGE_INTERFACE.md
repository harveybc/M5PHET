# Questions are the product interface

Owner clarification, 2026-09-24. Required product behavior, not an implemented
API claim. This corrects the interpretation that natural language is merely an
optional convenience over a plugin catalog. Satoshi owns implementation.

## The promise

Provide data or a data reference, context/description, a natural-language question
and optionally a requested output schema. Receive a structured, task-grounded
answer. Users should not need to know plugin groups, tensor axes, internal task
IDs or model-loader methods to ask a supported question. The explicit typed API
remains available for programs and reproducible jobs.

Examples of the SAME application surface:

| Input and question | Task-grounded answer |
|---|---|
| News and asset: "Is this relevant to EURUSD?" | Related/unrelated/unclear with the classifier's probability semantics |
| Price series: "Forecast the return in 6 and 72 hours, with 90% intervals." | Target/horizon-indexed forecasts and intervals, or named unsupported uncertainty |
| Observable market history: "Which hierarchical market state is this, and is it unfamiliar?" | Versioned cluster path and supported novelty measure |
| Portfolio and market state: "What target position does my configured policy recommend?" | Policy proposal with units, constraints and model identity; no executed order |
| Calendar and prices: "How does an above-consensus release affect returns over the next six hours?" | Identified effect curve and uncertainty, or explicit identification/data limitations |

Question wording and data are real inputs, not decorative labels attached to
five hard-coded example scripts. Domain profiles supply documented defaults
and selected providers so that users do not reconfigure the engine per question.

## Two execution routes, one public interface

**Native question-conditioned provider.** For supported classification, pass
the question/rubric and state to Laya's existing typed-question API, preserving
its semantics. Reuse upstream code; do not add a general LLM call in front of
every Laya request or retrain Laya to make the first slice work.

**Interpreted task with a specialized engine.** For a numerical or causal provider
without native question conditioning, a configurable interpretation component
converts question plus dataset description/schema into a bounded task proposal.
A deterministic resolver checks it against actual data metadata, installed
capabilities and the application profile, then dispatches to the existing engine.
If a language model is required, reuse an existing supported structured-output
client/provider; no new general-purpose agent framework, scheduler or code
generator. Interpretation is a role, not a sixth scientific ML family.

Both routes return the same result envelope. Numeric forecasts, probabilities,
policy actions and causal estimates come from the actual specialized provider,
not from prose generated by the interpretation component. A provider that directly
conditions on a question may bypass task interpretation when its contract allows;
this is not a requirement that all five families share Laya's pretrained weights.

```text
data + context + question + optional output schema
                    |
       resolve a supported task and its data bindings
                    |
        validate semantics, capabilities and permissions
                    |
       approved preparation + specialized provider
                    |
       structured result + resolved task + provenance
```

The data description may suggest meaning, but column roles, units and clocks
must agree with the actual registered schema. Infer safe structure automatically
where unambiguous, apply visible profile defaults, and ask only for materially
ambiguous missing semantics. Never invent what an undocumented column means.
Do not require manual tensor/config assembly on the normal user path.

The question selects the task; it does not grant resource or trading authority.
Preparation and fitting may be resolved into explicit internal operations when
the application's existing policy authorizes them. If no suitable fitted model
exists and fitting is not authorized, report that fact without synthesizing a
forecast. Do not start a training search because a question mentions prediction.
No policy change, new training budget or real-capital permission is implicit here.

## Retained resolved task and data boundaries

Retain question/context hashes, interpreter/provider revisions, data bindings,
applied defaults, transformations, output schema and resolved engine request.
Replaying that request must not reinterpret the question with a newer language
model. Reuse the existing registry/lifecycle and evidence machinery, not a second
parallel task runtime. Governed and local profiles retain their existing behavior.

The interpretation component receives schema and approved minimal context, not
an automatic upload of the full financial dataset. Remote text/model access is
explicitly configured; no silent remote fallback. News/data content cannot
override the application's instructions, permissions or source availability.
Typed input may include text and numerical data together; serializing a numerical
table into a prompt does not make Laya its forecasting model.

## Acceptance before implementation

| ID | Required public-path behavior |
|---|---|
| NL01 | Data + context + question reaches the real classifier without the caller supplying internal family/provider/task fields; SDK parity remains CL01 |
| NL02 | Non-template paraphrases of a numerical task resolve the same target, horizon, units and requested uncertainty; unsupported wording is not silently guessed |
| NL03 | Changing target, 6 hours to 6 observations, 90% to 95%, or input units changes/invalidates the resolved task appropriately |
| NL04 | Missing/contradictory schema, unavailable columns or unsupported output yields a specific clarification/refusal before engine work |
| NL05 | Numerical answer equals the native engine under the resolved task; retained-task replay invokes no interpreter and no implicit fit |
| NL06 | Instructions embedded in news/description cannot invoke code, change permissions, read another dataset or submit a broker order |
| NL07 | No valid model/identification/uncertainty support never produces invented estimates; material ambiguity is reported and profile defaults are disclosed |
| NL08 | Same public interface dispatches classification and forecasting end to end; then hierarchy, RL and causal routes advance independently with their own valid engines |

Tests use a sealed set of questions including unseen paraphrases, positive and
negative cases. Interpreter quality and numerical-model quality are separate
measurements. Fixture interpreters test plumbing only; actual language resolution
requires a real provider test. Specification checks cannot satisfy NL01-NL08.
